怎么读：三条规则

这套仓库的文档不是 API 手册，而是“什么时候该用哪个技能”的分布式路由。读法比读量重要。

docs 是导览，SKILL.md 是事实

docs 页面负责让你理解定位、边界和常见问题。真正执行时，技能行为以对应目录里的 SKILL.md 为准。两者冲突时，SKILL.md 赢。

先看调用方式

user-invoked 只能由你手打，例如 /implement。模型看不到它，也不会自动触发。model-invoked 可以由你手打，也可以由模型在任务匹配时自动触发。

按 flow 读，不按字母读

主链是 idea → ship。两个 on-ramp 分别接“别人交来的工作”和“已经坏掉的东西”。其余是 standalone 或词汇层。先建立这个骨架，再填细节。

每篇 docs 页的固定读法：What it does 看定义约束；When to reach for it 看触发边界；Prerequisites 看要准备什么；中间章节看它独有的概念；Common questions 看真实失败模式；It's working if 看验收信号；Where it fits 看它在图上的位置。

最短可用路线：1 → 3 → 4 → 6 → 9 → 12 → 13 → 16 → 14 → 15 → 19。大约 11 篇，足以跑通“有仓库、单 session 或多 session”的日常功能开发。

完整阅读顺序

按依赖顺序排列，不是按目录顺序。每读完一段，回到 ask-matt 的五个路线看一遍，你会知道刚读的节点挂在哪。

主流程图

实线是主链和直接分支，虚线是反馈或可选回路。每个框里的文字是“下一步动作”，不是技能简介。

主链 直接分支 反馈或可选回路
1setup-matt-pocock-skills：每仓一次，配置 tracker、标签和 domain docs。
2grill-with-docs / grill-me：把想法问到能承诺。有仓库用前者，没有仓库用后者。
3分支：谈不清就 prototype；缺外部事实就 research；答案在别人脑子里就 to-questionnaire。
4单 session：直接 implement，内部驱动 tdd 和 code-review。

7收尾：pr 写 PR body；retro 改环境；improve-codebase-architecture 把候选送回主链。

阶段边界：五个选项的顺序

阶段是 session 里的一块工作：访谈、实现、QA。边界只在两个阶段之间出现。按顺序问，第一个“是”就停下。

  1. 能继续吗？ 下一阶段需要这一阶段的原始上下文，或者 smart zone 还够。能就 Continue。它不丢信息，所以先排除它。
  2. 后面的工作和现在完全无关吗？ 是就 /clear。最便宜，但 wrong 了不可逆。
  3. 有东西需要移动吗？ 换 harness、换目录、交给同事、或中途分叉 side task，才用 /handoff。它买的是可携带性。
  4. 能 AFK 完成吗？ 任务边界足够紧，可以交给 subagent，当前 session 不动。
  5. 以上都不是，用 /compact。 它是默认，不是第一选择。给它一句“接下来要做什么”，让摘要保留下一阶段需要的东西。

为什么 compact 在最后：Continue 保留全部信息，clear 最便宜，handoff 最可携带，subagent 最隔离。compact 是“相关上下文、同 harness、同目录、还要在场”时的兜底。先选 compact 的典型后果是：新 session 对某个被摘要压平的决策过度自信。

常见坑

setup 不创建标签

它只写映射文件。GitHub 上要自己 gh label create 五个状态和两个分类标签，否则 ready-for-agent 会报 label 不存在。

不要把 to-tickets 的票再 triage

tickets 发布时已经是 ready-for-agent。triage 只处理外部进来的原始报告，重复 triage 会浪费 brief 工作。

implement 不关票，也不处理 review 发现

它结束在 commit。票的状态、acceptance criteria、review 修复都要你自己收尾。票不关，frontier 就不会前进。

code-review 看不到未提交改动

它比较 fixed-point...HEAD。implement 在 commit 前调用时可能没有可审的 diff。先 commit，再 review。

同一 session 里 review 自己有偏差

作者 session 带着所有假设。想要独立审查，就在干净 session 里对固定点跑 /code-review。

implement-spec 需要并行 subagent 和 worktree

不支持 worktree 的 harness 上，它只是更慢的 implement。票没有阻塞边时，整张图会同时开跑。

user-invoked 技能可能“显示不存在”

harness 把 disable-model-invocation 的技能排除在模型可见列表外。模型说没装时，直接手打命令，或查 .claude-plugin/plugin.json。

ask-matt 的摘要是二手信息

它按自己的摘要回答，可能滞后于 SKILL.md。要按它的建议行动前，先让agent打开对应 SKILL.md。

归档页不是当前功能

resolving-merge-conflicts 在 v1.3.0 移除，没有替代技能。冲突交给普通 agent 工作流。

完整实战：Course Video Manager

同一个项目从仓库配置跑到上线，覆盖主链、两个 on-ramp、维护回路和独立工具。项目是虚构的，但命令、产物和判断都是真实用法。你可以把 course-video-manager 换成自己的项目。

项目设定：一个 Next.js + TypeScript + Postgres 的课程视频管理器。已有模型是 Course、Section、Lesson。当一节 lesson 的视频处理完成后，它会被 materialize 成可播放的版本。

这个项目同时有四种工作：小功能“lesson 版本历史”、大计划“团队工作区与审批”、线上 bug“并发 materialize 返回 500”、维护问题“materialize 逻辑散落在多个 route”。四种工作刚好走完所有主流程和分支。

/ask-matt

1. 给 lesson 加版本历史，应该一个 session 能做完。
2. 做团队工作区和审批，很大，路线还不清楚。

02对齐小功能：grill-with-docs + domain-modeling

先做“lesson 版本历史”。这是一个 session 能定的功能，所以从有状态的访谈入口开始。

/grill-with-docs

我想给 lesson 加版本历史。
作者发布后还能看到每次修改，
并且可以恢复旧版本。

访谈会把含糊的词钉死。示例问题：

  • “版本”是整节 lesson 的快照，还是只记录标题和脚本？
  • 恢复旧版本时，是覆盖当前内容，还是创建一个新版本？
  • 评论跟 lesson 走，还是跟版本走？
  • 学生能看到历史吗，还是只有作者和管理员？

达成一致后，GLOSSARY.md 立刻长出条目，而不是最后批量写入：

## Lesson
一门课程里的最小教学单元。包含标题、脚本、视频资产和发布状态。
_Avoid_: video, chapter

## Version
Lesson 在某一时刻的不可变快照。恢复旧版本会创建一个新 Version，不修改历史。
_Avoid_: revision, draft

## Materialization
把上传的视频和脚本变成可播放 Lesson 的过程。
_Avoid_: processing, rendering

只有一个决定同时满足“难以逆转、脱离上下文会意外、真实权衡”，才写成 ADR：

docs/adr/0007-immutable-lesson-versions.md

Decision: Version 是不可变行。恢复操作复制旧快照为新 Version。
Reason: 历史必须可审计，回滚不能删除证据。

如果不在仓库里，同样的访谈用 /grill-me，但它不写 GLOSSARY.md 和 ADR。

03谈不清的 UI：handoff 出去，prototype 回答

访谈卡在一个问题上：“版本历史应该是右侧抽屉，还是独立页面？” 这属于谈不清、需要看到才能回答的问题。

/handoff "prototype version history drawer vs page"

# 新 session
/prototype

问题：版本历史在桌面端用右侧抽屉还是独立页面？
约束：移动端必须能单手操作。

prototype 产出两个结构不同的 UI 变体，不是一个变体的三种颜色。你在浏览器里点完，答案是一句话：桌面抽屉、移动端全页。

  • 原型提交到 prototype/version-history 分支，不合并。
  • 实现 issue 里放一个 context pointer 指向这个分支。
  • 答案写回主线程，继续 spec 或 implement。
04缺外部事实：research 后台跑

实现前发现一个事实问题：能不能用 Vercel Blob 的条件写入来避免并发覆盖？不要靠猜。

/research "Vercel Blob conditional writes and ETag support"

它在后台读官方文档和源码，写一个带引用的文件，例如：

docs/research/vercel-blob-conditional-writes.md

结论是“用内容 hash 作为 key，不依赖条件写入”。这个文件不自动进入后续 session，需要你把它带进 grilling 或 spec。

05答案在别人脑子里：to-questionnaire

还有一个问题不该问你：“助教能不能恢复版本，还是只有 owner 可以？” 答案在产品负责人脑子里。

/to-questionnaire

收件人：产品负责人
我需要拿回：角色权限矩阵、审计要求、是否允许助教恢复

它只访谈“发送”，不访谈主题。输出：

to-questionnaire-version-permissions.md

对方异步填完，答案回到 grilling 或 to-spec。不要为三个不同的人写一份问卷，一次只写给一个人。

06单 session 交付：implement + tdd + code-review + pr + retro

小功能已经对齐，直接构建。先创建一张票，或者用对话里的计划。

/implement #212

票的内容示例：

#212 Lesson version history

Demo: 打开一节 lesson，恢复 version 3，
看到系统创建 version 4，version 1 到 3 仍在。

Seams: LessonVersionService.list
        LessonVersionService.restore

Blocked by: none

一次 run 的五步：

  1. 读票，复述要构建什么，不重新设计。
  2. 在 LessonVersionService 的接缝上驱动 /tdd，一次一个红绿切片。
  3. 频繁 typecheck，单个测试文件随跑。
  4. 最后跑一次全量测试。
  5. 跑 /code-review，然后 commit 到当前分支。

一个红绿切片长这样：

红：restore creates a new version and leaves history unchanged
绿：只写 restore 需要的最小代码
红：list returns versions newest first
绿：补上排序

commit: feat: add immutable lesson versions

commit 后在干净 session 里再跑一次独立 review，固定点用分支起点：

/code-review main

然后写 PR body：

/pr

## Summary
Lesson detail 增加 history drawer，
restore 创建新 Version，不修改旧行。

## Evidence
Before: GET /api/lessons/42/versions -> 404
After:  GET /api/lessons/42/versions -> 200，3 条记录

## Merge Danger
Two-way door。爆炸半径：lesson detail API 和 history drawer。

最后复盘：

/retro

只接受能指向具体失败时刻的候选。比如“每次新增写接口都加并发测试”变成 CI 检查，“不要直接写 versions 表”变成 reviewer 标准。不要把所有东西都塞进 CLAUDE.md。

注意：implement 不会关闭 #212，也不会处理 review 发现。票的状态和 acceptance criteria 要自己收尾。

07大计划：wayfinder 画决策地图

“团队工作区与审批”不是一个 session 能装下的，而且路线不清楚。不要直接 grill 到底，也不要直接开票。

Destination:
一个团队可以邀请成员、分配角色，
并在发布前审批一个课程版本。

/to-spec #300

/to-spec #300

09两种构建方式：implement 逐票 vs implement-spec 并行

方式 A：逐票，人在场。

/clear
/implement #341
# commit 后手动关票
/clear
/implement #342

每张票一个 fresh context，票之间不共享上下文。适合你想逐票阅读、随时调整方向。

方式 B：整 spec 并行。

/clear
/implement-spec #340

编排 agent 把票当 task graph，在各自 worktree 里并行跑 ready frontier，合并到一个 integration branch，最后跑一次 code-review。需要 harness 支持后台 subagent 和 worktree，否则它只是更慢的 implement。

并行前检查冲突：#342 和 #343 都可能改 workspace/members.ts。给它们加一条阻塞边，或者在 exploration notes 里固定共享命名。worktree 不会消除冲突，只会把冲突推迟到 merge。

10线上 bug：triage → diagnosing-bugs → retro

用户报告：“两个人同时完成 lesson 视频时，materialize 偶发 500。” 这是别人交来的原始报告，先 triage。

/triage #401

triage 不只看文字，它先复现：

  • 开两个并发请求，确认 500 能出现。
  • 检查是否已经实现、是否在 .out-of-scope/ 被拒绝过。
  • 写 agent brief：POST /api/lessons/:id/materialize 必须幂等；并发时只能有一个成功写入。
  • 状态标为 ready-for-agent。

然后进入诊断。Phase 1 是唯一困难的阶段：先建一个 tight loop，没有红命令就不准提假设。

pnpm repro:materialize-race
# 期望：并发两个请求，至少一个 500
# 要求：秒级、确定性、断言这个具体症状

后续阶段：

  1. 最小化复现：两个请求指向同一 course，去掉无关字段。
  2. 列 3 到 5 个可证伪假设：缺唯一约束、事务隔离级别、共享临时目录。
  3. 一次变量一个探针，日志带 [DEBUG-a4f2]。
  4. 修复：INSERT ... ON CONFLICT 加 advisory lock。
  5. 回归测试先写，确认在原提交上红。

修完后在同一个 session 跑 /retro，问“什么能预防这类 bug”。这次答案不是一句提醒，而是并发 materialize 的 CI 测试和“新写接口必须有幂等测试”的检查。

11代码健康：improve-codebase-architecture

审批功能做完后，代码里出现一个信号：materializeLesson 的逻辑散在三个 route 和两个 job 里。跑一次巡检。

/improve-codebase-architecture "how can we make the approval feature easy?"

它不改代码，只产出临时 HTML 报告和候选。一个候选：

深模块：LessonMaterializer
问题：materialize 流程在 5 个调用方重复，测试要分别 mock
删除测试：删掉它，复杂度会回到 5 个调用方，而不是消失
收益：locality 提高，审批发布路径只需要观察一个接缝

选中候选后，用 grill-with-docs 把约束问清，用 codebase-design 的词汇讨论 module、interface、depth、seam、adapter。然后回到主链：

/to-spec
/to-tickets
/implement

这不是“重构周”，而是一个候选 idea 重新进入主链。

12人工步骤：wizard 生成交互式向导

审批功能需要 staging 的 S3 bucket、Resend API key 和 webhook secret。这些只有人能点，agent 不该把步骤丢进聊天。

/wizard "set up S3, Resend, and webhook secret for staging"

它先读仓库里的 .env*、docker-compose* 和 GitHub Actions 里的 secrets.*，确认要生产哪些值，然后给你一个有序 stage 列表：

  1. 创建 S3 bucket，复制 ARN。
  2. 创建 Resend API key。
  3. 把值写入 .env.staging 和 GitHub secrets。
  4. 跑一个最小 smoke test。

agent 写脚本，不运行。你在自己的终端执行，敏感值不会进入模型上下文。

13上下文与交接：什么时候 clear、handoff、compact

这个项目里每个边界都做一次选择：

边界选择原因
grilling → to-spec → to-ticketsContinue下一阶段需要访谈的原始推理，不能丢
to-tickets → 每张 implement/clear每张票自包含，上一张的上下文可丢弃
主线程 → prototype 目录/handoff换目录，原型上下文不该污染主线程
Claude Code → Codex/handoff换 harness，旧上下文不可见
同一 harness，继续下一阶段/compact相关上下文还要用，但窗口需要压缩
code review 或 researchsubagent任务边界紧，可以 AFK

顺序不要反：先问能不能继续，再问能不能 clear，再问有没有东西要移动，再问能不能 AFK，最后才是 compact。

合并冲突不再有专用技能。resolving-merge-conflicts 在 v1.3.0 已移除，冲突交给普通 git 加 agent 工作流处理。

14沟通与学习：teach、wait-what、writing-for-agents

做审批功能时，你需要理解 Postgres row-level security。不要在主线程里边做边学，开一个独立教学工作区：

mkdir learn-rls
cd learn-rls
/teach "Postgres row-level security for multi-tenant workspaces"

它先访谈 mission，再建 RESOURCES.md、lessons/*.html、learning-records/*.md。下一节课在新 session 里说“next lesson”即可继续。

当 agent 说“RLS policy 使用 security definer function 和 leakproof wrapper”而你没听懂：

/wait-what

它会把这句话用更少的词和缺失的上下文重讲一遍，并优先使用 GLOSSARY.md 里的词。

最后，把团队的 agent 规则写短：

/writing-for-agents

为这个仓库写一份 AGENTS.md：
- 安装、测试、typecheck 命令
- 哪些目录不能直接 import
- 新接口必须有幂等测试
- PR body 用 Summary / Evidence / Merge Danger
- 不要写通用的“写好代码”建议

目标是删掉 no-op，不是把文档写长。

建议的第一次实操

读完 1 到 19 后，用一个真实的小功能跑一遍。不要先跑完整清单。

  • 在目标仓库运行 /setup-matt-pocock-skills，确认 docs/agents/ 下三个文件出现，并手动创建 tracker 标签。
  • 拿起一个你熟悉的小需求，在仓库里手打 /grill-with-docs，观察 GLOSSARY.md 是否在访谈过程中逐条变化。
  • 如果需求跨多个 session，接着在同一上下文里运行 /to-spec，不要 clear；再运行 /to-tickets，检查每张票的 “demo 什么”。
  • 清空上下文，按票运行 /implement。在 trace 里确认它调用了 tdd，并在最后调用了 code-review。
  • commit 后，在干净 session 里运行一次 /code-review，固定点用分支起点。对比两次 review 的差异。
  • 合并或开 PR 前，用 /pr 生成 body，检查 Summary 是否一张图就能看懂、Evidence 是否有前后对比、Merge Danger 是否明确。
  • 最后运行 /retro，只接受能指向具体失败时刻的候选，把机械错误变成检查，而不是继续加 CLAUDE.md 句子。
